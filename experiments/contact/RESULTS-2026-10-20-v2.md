# DeepSeek contact pilot follow-up — 2026-10-20

Status: completed exploratory experiment; **candidate rejected for promotion**.

The unchanged instruction and its four-sample majority baseline each scored
**36/36 exact records** on newly generated held-out inputs. The frozen Harness2
instruction scored **28/36 (77.8%)**, with eight regressions and no improvements.
All regressions occurred in the nine-case ambiguity group. This is evidence
against deploying this artifact, not a general verdict on Harness2.

## Protocol and execution

[ADR-0003](../../docs/adr/0003-cumulative-usage-budget.md) was accepted and
[protocol version two](protocol-v2.json) preregistered in `f4bae38` before further
experimental inference. It changes cumulative accounting; version one's quality,
selection, isolation and freeze rules remain unchanged. The original
[incomplete-pilot report](RESULTS-2026-10-20.md) remains historical evidence.

The qualified run, `contact-pilot-v5`, completed **12/12 development tasks with
no fallback**, using parallel `k=1`. Its 48 bounded proposer sessions produced
48 execution rollouts and 56 solver requests, including eight repair attempts.
The per-task adopted outputs scored 11/12 after selection; development base and
four-sample baseline each scored 12/12. Operational completion did not imply
factual correctness.

The final task's adopted instruction was frozen without consulting gold:
`1ececefb97a07e68509a78cefc15b4364824b3eab8030947a1a62c8be06e8a25`.
Only then were 36 new cases generated, nine per preregistered cluster. Their
inputs were transferred to the VM; answers stayed on the host until execution
finished. Dataset identity, raw outputs, selections, accounting receipts and
source provenance are in the [released evidence bundle](../../docs/evals/contact-pilot-2026-10-20/README.md).
These released cases are no longer fresh held-out data for a later campaign.

## Diagnosis and decision

The frozen artifact instructs the model to emit an array when several contacts
appear, contradicting the runtime's fixed single-object contract. Nine initial
responses failed the independent schema check. Repair recovered a valid object
in seven cases; two runs remained rejected. A valid object could still select
the wrong contact. The unchanged runtime gates were retained throughout.

The adapter's public task prompt states fields and null handling, but does not
explicitly convey single-object cardinality or the preregistered primary-contact
ambiguity policy to the proposer. This limits interpretation: the negative result
belongs to this adapter/profile, and cannot isolate Harness2's general ability.
A follow-up should make that public task contract explicit before tuning, then
preregister a new experiment with fresh held-out inputs. This artifact and these
36 answers were not used for a post-hoc repair or second selection.

**Do not promote the frozen instruction.** Keep the built-in instruction as the
default. No service was deployed or restarted, no runtime tool was approved, and no Xbox
or xLlama model was contacted. The accepted second phase remains separate.

## Regression control

The original **87 dev cases passed 87/87 in both arms**. No case changed pass/fail.
The three existing held-out turn cases were excluded. All 84 non-`extract_contact`
first requests had identical message bodies and token limits across arms.
Only three cases exercise the typed extraction instruction seam: a green 87-case
control therefore does not cover the ambiguity failures found by the new set.
Regression requests retained their original fixture token limits; both arms used
DeepSeek Flash at temperature zero and the same checked catalog.

## Failure corrections and provenance

After accounting migration, attempt v3 stopped on empty OpenCode replies. The
previous path had not set proposer temperature explicitly. The gateway now
forces temperature zero and retains redacted provider events. Attempt v4 showed
that temperature alone did not fix missing final output: sessions could spend
their turn budget inspecting files and edit the instruction before saving their
answer. A bounded proposer profile now batches inspection and requires the
answer to be saved with the edit. The failed selection passed a single controlled
canary before the new v5 run. Both incomplete attempts remain archived; no quality
claim uses their partial outputs.
